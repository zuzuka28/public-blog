Стенд для обучения работы с сетевыми протоколами

Размышления о демонстрации работы сетевых протоколов
Дата публикации

3 августа 2026 г.

Я занимаюсь разработкой распределенных систем и периодически мне на глаза попадаются статьи и книги о деталях реализации сетевых протоколов.

Я не сетевой инженер, поэтому мои знания обо всех деталях того, как работают протоколы довольно ограничены: что-то слышал, что-то проходил в рамках курсов, но никогда не занимался реализацией собсвенных протоколов на низком уровне.

Мне хотелось бы самому лучше разобраться в деталях и помочь другим интересующимся изучить тему, поэтому я хочу реализовать приложение, которое позволит детерменированно симулировать и тестировать работу протоколов.

Я слышал умные слова, но не трогал и не представлял, как в реальности выглядят следующие приемы:

  • retransmission
  • buffer management
  • sliding window
  • crc checksum
  • sequence numbers
  • reassembly
  • error detection
  • error correction

Я знаю, что эти приемы как-то связаны с решением следующих проблем:

  • работа при потере пакетов
  • работа при задержке пакетов
  • работа при дублировании пакетов
  • работа при ошибке в пакете
  • работа при ошибке в последовательности пакетов
  • работа при отставании читателя или писателя

Но не знаю, как каждый подход связан с решением конкретной проблемы.

Я хочу понять, как реальные протоколы по типу TCP/UDP/IP передают данные и почему мы можем полагаться на их работу.

Почему нужен специальный стенд для обучения?

Реализация учебного протокола требует контролируемой среды, где можно управлять скоростью передачи данных, задержками, потерями пакетов и другими параметрами.

Также требуется отказаться от использования реального времени, потому что тогда стенд будет медленным и недетерминированным - вместо этого будут использовать внутренние виртуальные таймеры, которые будут точно выполнять действия в заданное время.

Первая задача: создание корректной абстракции

Первой задачей, с которой я столкнулся при реализации стенда, было создание корректной абстракции, чтобы пользователи были ограничены и занимались именно реализацией протокола.

Изначально я хотел предоставить абстракцию, близкую к net/http из Go, что-то типа:

type Server interface {
    Handle(ctx, req *Request) (*Response, error)
}

type Client interface {
    Do(ctx *Context, req *Request) (*Response, error)
}

Клиент отправляет запрос, сервер получает запрос и отвечает.

Но протоколы, которые я хотел рассматривать, могут работать и на более низком уровне, чем HTTP - основная часть приемов, которые меня интересуют работают с последовательностями байт, что ближе к net.Conn.

type Conn interface {
    Read(ctx *Context, p []byte) (n int, err error)
    Write(ctx *Context, p []byte) (n int, err error)
    CloseWrite(ctx *Context) error
    Close() error
}

После некоторого изучения стало понятно, что для реализации и тестирования протоколов (и наблюдения за их поведением), более удобным способом представления протокола будет не прикладной интерфейс взаимодействия, а набор реакций на происходящие события - отправку и прием данных, либо истечение некоторых временных ограничений.

Тогда пользователь будет реализовывать протокол в виде набора реакций на события:

type ProtocolContext interface {
    // send packet to network layer
    SendPacket(p []byte) error

    // submit to application layer
    SubmitToApp(msg []byte) error

    // virtual time
    SetTimer(id string, timeout time.Duration) error
    CancelTimer(id string) error
}

type Protocol interface {
    // called when application layer writes message
    OnAppWrite(ctx ProtocolContext, msg []byte) error

    // called when network layer receives packet
    OnRecievePacket(ctx ProtocolContext, p []byte) error

    // called when timer expires
    OnTimer(ctx ProtocolContext, id string) error
}

Предоставляя пользователям хорошую абстракцию, можно симулировать работу протокола без использования реальных сетевых интерфейсов.

Для изучения большинства приемов достаточно одной пары клиент-сервер, поэтому мультиплексирование и управление несколькими соединениями будет вынесено за рамки данного цикла упражнений.

Отправка транспорных пакетов и контроль последовательности доставки далеко не самый первый слой в сетевом стеке. Зачастую канал передачи данных не является надежным, поэтому поверх канала передачи данных присутствует еще и канальный протокол, который будет отвечать за целостную передачу пакетов по ненадежному каналу.

type ChannelProtocolContext interface {
    // send bits to channel
    SendBits(p BitSlice) error

    // submit to application layer
    SubmitToApp(msg []byte) error
}

type ChannelProtocol interface {
    // called when channel receives bits
    OnRecieveBits(ctx ChannelProtocolContext, p BitSlice) error

    // called when channel sends bits
    OnAppWrite(ctx ChannelProtocolContext, msg []byte) error
}

Помимо отправки сообщений через транспорт, многие протоколы используют дополнительное кодирование данных для повышения эффективности передачи. Кодирование может быть реализовано на разных уровнях: как перед вызовом транспортного протокола, так и перед передачей в канальный протокол.

type Codec interface {
    Encode(msg []byte) ([]byte, error)
    Decode() ([]byte, error)
}

Вторая задача: обозреваемая работа протоколов с симуляторов

Чтобы пользователи могли тестировать и наблюдать за работой написанного ими протокола, требуется реализовать симулятор, через который будет проходить каждый этап обработки сообщений, а не только первый и последний этапы. Связка протоколов должна целиком работать через коммуникацию с симулятором, который будет посылать управляющие сигналы между протоколами.

Текущая идея - написать управляющий компонент, который будет единой точкой отслеживания всех событий, а реализация протоколов будет лежать на небольших приложениях, которые будут общаться с помощью json через stdin/stdout через sdk симулятора. Это не полный language agnostic подход, но с по крайней мере он позволит меньше зависеть от конкретного языка, на котором будут писаться обработчики.

Для полной обозреваемости можно строить систему как flow движок, где пользователь сможет указать ноды с собственными протоколами. Потенциальные ноды:

  • отправка сообщения (можно ввести любой текст для отправки)
  • кодирование / декодирование (дополнительный слой модификации данных перед передачей в другие узлы)
  • пакетный протокол (работает с пакетами и байтами)
  • канальный протокол (работает с пакетами и битами)
  • модицикация события (может быть использована для добавления задержки, потери пакетов, дублирования пакетов и т.д.)

Каждый компонент может запускаться как отдельное приложение, в gui будет попадать информация о результатах работы каждой ноды, чтобы можно было отобразить поэтапную работу каждого компонента.

Из нюансов: в реализации самой ноды может быть внутреннее состояние, которое никак не отобразить в gui, которое могло бы быть полезным для отладки.

Где применимы собственные протоколы?

В настоящее время нельзя написать собственный протокол, который бы выполнял роль UDP/TCP/IP, потому что реализации этих протоколов уже содержатся в операционных системах. Собственные протоколы можно использовать только если будут системы, которые поддерживают написанные протокол, что в основном значит, что требуется перекомпилировать систему с написанным протоколом.

Наиболее близким опытом к созданию транспортного протокола является реализация собственного прикладного протокола поверх стека UDP/IP - UDP является протоколом без состояния, поэтому все нюансы управления соединением будут реализованы в прикладном протоколе.
